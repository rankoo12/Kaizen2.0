## Root cause (what the evidence actually showed)

Not "assertions don't wait" (assert_text already polls ~8s). On a
still-rendering page the only control present is persistent chrome; the
candidate ranker picks it, and the name-blind element-embedding cache
rubber-stamps it — the Notifications bell was served for "Add friend", "Play",
"Block", "Create event"; the composer for "the comment field"; a stale redis
entry served the "Messages" nav link for "the Mira Chen conversation". The
action then fires on the wrong element and the honest assert fails downstream.

## The fix (src/workers/worker.ts + name-fidelity.ts)

When an interaction's resolved element shares **zero salient words** with the
step's target (`nameAbsent`, unit-tested) — or a fill action lands on a link —
the worker now: **evicts the poisoned cache entry → settles patiently (600ms
quiet / 3s ceiling, ×3) → re-resolves cache-first → adopts only a non-suspect
result → restores the original otherwise.** Never worse by construction: a
correct-but-oddly-named pick (the renamed "Publish") is retried, not replaced,
and proceeds unchanged. The eviction step was the decisive piece — the first
verify run proved the retry loop was otherwise re-served the identical
poisoned selector all three times.

Two earlier attempts were tried and **rejected on evidence** (a score<=0.5
trigger over-fired and regressed the baseline; a no-evict loop recovered
nothing) — the shipped version is the one that survived verification.
